## 1. What the code does today (read 2026-11-28, branch phase-2-network-intelligence @ 9cb237c)

### PC → viewer (WebRTC path, `agents/endpoint-agent/internal/rdstream/webrtc.go`)

| Item | Value | Note |
|---|---|---|
| Bitrate | Min 300k, Start 2.5M, Max 12M | |
| FPS cap | 60 on LAN; `VideoFPSFor`: 30 if RTT ≥ 60 ms or bitrate < 2.5M; 20 if RTT ≥ 160 ms or bitrate < 1M | |
| RTT cap (`MaxBitrateForRTT`) | ≥ 80 ms → 5M, ≥ 140 ms → 2.5M, ≥ 220 ms → 1.2M | |
| adapt() every 2 s | down 30 % if loss > 15 % or RTT ≥ 260; down 20 % if loss > 10 %, or loss > 5 % with RTT ≥ 80, or **RTT ≥ 180**, or jitter ≥ 50, or ≥ 3 PLI; **up 10 % only when RTT < 120 ms** and loss < 2 % | between 120 and 180 ms the bitrate never climbs back; through DERP (~170 ms) a dip is never recovered |
| Scale (`VideoScale`) | 100 % ≥ 2M, 75 % below 2M, 50 % below 900k | |
| Congestion control | `RegisterDefaultInterceptors` only: NACK, RTCP reports, stats, TWCC *header extension + feedback for streams we receive*. **No GCC bandwidth estimator, no pacer.** | the browser sends TWCC feedback, nobody reads it; the bitrate is driven only by RR loss, ICE RTT, jitter and PLI |
| Sending | `WriteSample` of a whole frame at once | a keyframe goes out as one burst of packets, no pacing |
| Encoder (`videoenc/mf_windows.go`) | Media Foundation, CBR, low-latency, **GOP = FPS × 2 (a keyframe every 2 s)** | a big burst every 2 s on top of PLI keyframes |
| RTP size | pion `outboundMTU = 1200` | 1200 + SRTP tag 10 + UDP/IP 28 = ~1238 < Tailscale 1280: **no fragmentation expected** (to confirm with a capture) |
| ICE | UDP4/UDP6 host candidates, STUN only if `RD_WEBRTC_STUN_URLS` is set (empty on the installed server) | over Tailscale both sides have a 100.x host address, so no STUN is needed; whether the WebView reaches it (mDNS / peer-reflexive) is to be checked |

### PC → viewer, WebSocket fallback (`stream.go`)
- H.264 over WS when WebRTC is busy/failed: `WSVideoBitrate(q)` = 1M + (q−25)·56k, starts ≤ 1.8M; adapt every 1.5 s: −25 % if RTT > 220, +5 % +50k if RTT < 130; −25 % on each frame not acked within 2 s.
- FPS: `VideoFPSFor(30, …)` → 30 at best, 20 when RTT ≥ 160.
- In-flight window: 6 frames, 8 when RTT ≥ 150 ms.
- This is TCP: inside Tailscale (WireGuard/UDP when direct, **TCP when through DERP** = TCP over TCP).

### Phone → viewer (`agents/android-agent/.../LiveStream.kt`, `VideoPlan.kt`)
- Always WebSocket through the server (no WebRTC from the phone).
- **`MAX_FPS = 15`** on any network.
- Bitrate = 1M + (q−25)·110k, starts ≤ 2M; −25 % if RTT > 220; +5 % +50k if RTT < 130; capped at 1.6M (RTT ≥ 220) / 1M (RTT ≥ 300).
- Encoder: MediaCodec VBR, keyframe every 5 s.

### 3.5 MTU
Tailscale adapter MTU 1280. Largest ping with Don't Fragment: 1252 bytes payload (1253 is refused).
pion sends RTP of ≤ 1200 bytes (+ SRTP tag, ≈ 1210 bytes UDP payload), so **no fragmentation**.
Not a cause.

### 3.6 Other traffic on the same link
With the PC page open on the phone and **no** video, the PC still sends the phone 860 kbit/s on
average, in bursts of 2.0–2.9 Mbit/s every ~4 s. Cause: `endpoint-detail-screen.tsx` re-reads
`/api/v1/endpoints/:id` every 4 s; that answer is 342 KB, and on the phone's HTTPS listener it is
**not compressed** (the API has no compression; the browser on the PC gets it through Next.js gzip:
47 KB). During the WebRTC run the PC sent 1 130 kbit/s on average for ~290 kbit/s of video.

## 4. Main cause (with evidence)

1. **Our own adapt rules hold the picture at the minimum on any relayed link.** `NextBitrateFor`
   only lets the bitrate climb when RTT < 120 ms, and cuts it 20 % whenever RTT ≥ 180 ms. Through
   DERP the RTT is never below 130 ms and often above 180, so the bitrate walked down to
   300 kbit/s and stayed there for 3 minutes with **0 % loss**, while the same path carries 4 Mbit/s
   of UDP with 0 % loss. `VideoScale` then drops the picture to 960×540 and `VideoFPSFor` caps it at
   20 fps (RTT ≥ 160). On the LAN the same code goes to 12 Mbit/s, 1080p, 45 fps. → Low quality and
   the 20 fps ceiling away from home come from the code, not from the link.
2. **The path is always relayed (DERP), never direct, on 4G today.** RTT 130–830 ms with spikes and
   seconds-long TCP stalls; the region changes between runs. PC→phone tops out near 4 Mbit/s.
   Why hole punching fails is not known yet (it worked once on 2026-11-27).
3. **Phone → PC is held back by acks, not by bandwidth.** The phone sends 265 kbit/s on a 6 Mbit/s
   link; ack RTT 1–2 s and frozen; fps 5–12. The frame window waits for acks that come back late
   through TCP-over-DERP. Plus the 15 fps cap.
4. **The dashboard itself loads the link**: 342 KB uncompressed every 4 s (≈ 0.9 Mbit/s with
   2–3 Mbit/s bursts) on a path that has ~4 Mbit/s, which pushes RTT up and feeds cause 1.

Not causes: MTU/fragmentation (3.5), packet loss on the relay below 4 Mbit/s (3.2).

## 5. What this means for Phase 2 (proposal, not started)

- Cheapest and biggest first (code only, no VPS): (c) adapt on loss and queue growth instead of an
  absolute RTT line, with hysteresis and WAN limits apart from LAN; FPS not tied to RTT; scale
  first, then bitrate. Compress the API answers on the HTTPS listener and slow/trim the 4 s
  endpoint re-read. Phone→PC: a bigger frame window / ack scheme fit for 200+ ms.
- (b) Why hole punching fails on Vodafone 4G: needs a look at the phone side (Tailscale's
  `debug` view on Android or a STUN test from the phone).
- (a) Own DERP: Paris is the nearest city from both WE (57 ms) and Vodafone (99 ms) — the **same city**
  as Tailscale's DERP, so it would help only with relay capacity/steadiness, not distance. Worth it
  only after the code fixes, if relayed sessions are still unsteady.
