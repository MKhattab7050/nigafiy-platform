# Security review, November 2026

Builder SEC1, branch `worktree-security-review` (cut from `phase-2-network-intelligence` at 449c505).
Method: source review of every area named below, confirming each finding in code before it is
listed; fixes are one commit per finding with a regression test. Nothing was run against a real
network, router or device; everything below is verified by tests on this PC (loopback only) unless
it says otherwise. Findings labelled "EXT-n" came from an outside reviewer's list and were checked
against the current code here.

Severity: **critical** (remote takeover of managed machines without credentials), **high** (a
signed-in user or a single compromised piece gains what its role or consent should not give),
**medium** (needs extra conditions, or limits damage), **low** (hardening / defence in depth).

### SEC-01 (high): admin → any member through a self-made identity provider

- Where: `apps/api/src/modules/auth/sso/admin.ts` (create/patch/delete were `requireRole('admin')`),
  `apps/api/src/modules/auth/sso/users.ts:resolveSsoUser` (matches an existing user by email),
  `apps/api/src/modules/auth/sso/routes.ts:finishSignIn` (`trust_idp_mfa` skips local TOTP).
- Attack: an admin (not owner) creates an OIDC provider pointing at an IdP they run, lists the
  organization's email domain as allowed and sets `trust_idp_mfa: true`. Their IdP asserts
  `email = owner@company` (or another admin's address). `resolveSsoUser` finds the existing user by
  email, the user has an active membership in the organization, so the sign-in succeeds as the
  owner, without the owner's password or TOTP. The same works for impersonating a second admin and
  approving one's own "second-admin approval" request for an unattended remote session
  (`fleet-policy/approvals.ts`), which defeats the two-person rule.
- Fix: creating, changing and deleting an identity provider is owner-only (admins still list
  providers and run Check); the web Settings card hides the write buttons and says why (EN + AR).
  Regression test: `apps/api/tests/sso.test.ts` "is admin-readable and owner-writable".
- Residual: the owner can still impersonate any member through a provider; the owner already holds
  every power in the organization, so this is recorded, not fixed. Domain ownership of
  `allowed_email_domains` is not verified (a DNS TXT proof would close the "any domain" part).

### SEC-02 (high): Quick Support files before consent

- Where: `apps/api/src/modules/endpoints/commands/service.ts:queueCommand` allowed `fs_op` on a
  `kind = 'quick_support'` endpoint whenever it was online; the session/consent gate there covered
  only `rd_capture`/`rd_input`. The program side (`cmd/nigafiy-support/main.go:Limited`) allows
  `fs_op` and `notify_user` at any time.
- Attack: the person runs Quick Support and the code waits for their IT contact. Every technician
  sees waiting codes and their `endpoint_id` in `GET /fleet/quick-support`. A technician (any one,
  not the person's contact, without the code or PIN) sends `POST /endpoints/<id>/commands
  {kind:'fs_op', op:'list'|'download', ...}` and browses or downloads the person's files; an admin
  can upload. The person never saw an Accept dialog.
- Fix: on a Quick Support computer, `fs_op` needs an open session that the person accepted
  (`state = active`) and the requester must be a participant of it (refusal audited as
  `fleet.session_refused_action`); automation (`queueEndpointCommandFor`) never targets Quick
  Support computers. Regression test: `apps/api/tests/fleet-reach.test.ts` Quick Support case
  (`no_remote_session` before connect, `consent_pending` before Accept, nothing delivered).
- Residual (low, open): the program itself still runs `fs_op` whenever the server sends one; a
  compromised server is outside this threat model, but the program could keep its own "session
  accepted" flag as a second gate.

### EXT-3 (medium, confirmed): remote shell without its banner

- Where: `agents/endpoint-agent/internal/shell/shell.go:Open` (was line 201): a banner error was
  logged and the PowerShell/PTY session joined the server anyway, as the agent's service account.
- Attack: on a computer with a signed-in person, anything that makes the banner fail (the user UI
  helper crashed or refused, a session switch at the wrong moment) gave the operator a SYSTEM shell
  the person never saw, contrary to the transparency rule ("no shell without the banner").
- Fix: when the computer has a desktop (`Config.Banner` set) and the banner cannot be shown, the
  terminal is closed and the shell is refused before the server socket is dialled; the command
  result says why (`banner: failed`). A computer with no desktop at all (`Banner` nil, a headless
  server: nobody to inform) keeps opening with `banner: unavailable`, which the operator sees.
  Regression test: `internal/shell/shell_test.go` `TestBannerFailureRefusesTheShell`.

### EXT-4 (medium, confirmed): command ids forgotten all at once

- Where: `agents/endpoint-agent/internal/agent/agent.go` poll and stream dispatch: `seenCmds` was
  `clear()`ed whenever it reached 2048 entries.
- Attack / failure: remote desktop input and capture are commands too, so 2048 ids pass in minutes.
  Right after the clear, a command that had just run (restart, software removal, config restore,
  a script) runs again if the same command is handed out again (a retried poll response, the
  stream and the poll both carrying it). The server marks commands delivered, so this needs a
  repeat delivery, hence medium.
- Fix: `internal/agent/seen.go` `seenSet`, a bounded set with oldest-first eviction (8192 ids), so
  a recent id is never dropped to make room. Regression test: `internal/agent/seen_test.go`.
- Residual (low, open): the set lives in memory; after an agent restart a command the server
  hands out again would run again. The server side (delivered_at, single delivery) is the main
  guard; persisting the last ids in the state folder would close it.

### EXT-6 (medium, confirmed): mention and link injection in Slack and Discord

- Where: `apps/api/src/modules/notifications/channels.ts` `renderSlackPayload` put event titles,
  site names and details (which carry device-supplied hostnames, DHCP names, SNMP strings) into
  mrkdwn unescaped; `renderDiscordPayload` did not limit mentions.
- Attack: anyone on a monitored LAN names a device `<!channel>` or `@everyone`, or
  `<https://evil.example/login|Open Nigafiy>`; the next "new device" or "device down" alert pings the
  whole channel or shows a forged link inside a trusted alert.
- Fix: Slack text is escaped (`&`, `<`, `>`, per Slack's formatting rules); Discord payloads carry
  `allowed_mentions: { parse: [] }`. Checked the others: Telegram was already HTML-escaped, email is
  plain text, ntfy headers are ASCII-stripped single lines, webhooks are JSON. Regression test:
  `apps/api/tests/notifications-channels-and-escalation.test.ts` "renders safe payloads".

### EXT-9 (low, confirmed): log redaction narrower than documented

- Where: `apps/api/src/infrastructure/logger.ts` redacted only `password`, `token`, `credential`,
  `secret` (top level and one level down) and auth headers; `engine/internal/logs/logs.go:Redact`
  (which writes every child's output to disk) removed only `ld*_` token prefixes.
- Risk: no current log call was found that prints an SNMP community or router password, so this is
  defence in depth: a future `logger.info({ body })` or a child process printing
  `community=public` / `"router_password":"..."` would have written it to disk.
- Fix: the API redacts a named list (`REDACTED_FIELDS`: passwords incl. router/SMTP, SNMP
  `community`/`snmp_community`, v3 `auth_key`/`priv_key`/`auth_password`/`priv_password`, client
  secrets, webhook URLs, bot tokens, MFA/step-up tokens, recovery codes, auth headers) at the top
  level and two levels down; the engine also redacts the value of any JSON or `key=value` field
  whose name ends in password, passphrase, community, secret, token, credential, api key,
  private/auth/priv key, authorization or cookie. Regression tests:
  `apps/api/tests/logger-redaction.test.ts`, `engine/internal/logs/logs_test.go`.
- Residual: pino paths are names, not patterns; a new secret field name must be added to the list.

### EXT-1 (medium, confirmed): sign-in throttle per IP only

- Where: `apps/api/src/modules/auth/routes.ts` `credentialLimiter` (10/min per IP) was the only
  limit on `POST /auth/login`; no per-account counter (TOTP has its own lockout, passwords did not).
- Attack: a guesser with many source addresses (a botnet, a cloud range, IPv6 /64s) tries passwords
  against one known admin email at 10/min per address, unbounded in total.
- Fix: a second limiter keyed on the (normalized) email counts failed sign-ins from all addresses
  together: 20 failures per 15 minutes, then a generic 429 for that account. Failures are logged
  with the IP, a 16-hex-digit hash of the email (not the address) and whether the account exists.
  Regression test: `apps/api/tests/login-throttle.test.ts`.
- Lockout trade-off (documented in the code): someone who knows an email can keep that account from
  signing in with a password for 15 minutes at a time; existing sessions and SSO keep working.
  Spraying ONE password across MANY accounts is not stopped by a per-account limit; the per-IP limit
  and strong-password policy remain the controls there (a global failure-rate alarm is open).

### EXT-2 (medium, confirmed): WebSocket hubs without rate, count or liveness limits

- Where: `apps/api/src/modules/endpoints/remote-desktop/stream-hub.ts` (`onUpgrade`, `acceptViewer`)
  and `apps/api/src/modules/endpoints/fleet-shell/hub.ts` (`acceptOperator`). Operator sockets used
  the agents' WebSocketServer (8 MiB / 1 MiB `maxPayload`), messages were queued without bound
  (the stream hub handles them one at a time, each may write an audit row), any number of viewer
  sockets per user or session could be opened, every upgrade did a credential or session lookup
  without a cap, and nothing noticed a dead TCP connection (a viewer slot or a shell window stayed
  held until the OS gave up).
- Attack: a signed-in participant (or a stolen session cookie) floods a remote desktop socket with
  small messages: the in-order chain grows without bound in memory and the audit table with it;
  many sockets per user, or many unauthenticated upgrades from one address, cost a database lookup
  each. Needs a valid session or only exhausts resources, hence medium.
- Fix: `apps/api/src/common/ws-guard.ts` (`MessageRate`, `SocketCounter`, `heartbeat`). Operator
  sockets have their own servers with a smaller `maxPayload` (desktop 6 MiB text, the largest
  being a clipboard picture; shell 64 KiB, one paste), closed by `ws` with 1009 above it; above 300
  messages/s the extra ones are dropped and above 1500/s, or 512 waiting, the socket is closed with
  1008; at most 64 upgrades in flight per remote address (HTTP 429), 16 viewers per remote desktop
  session, 12 viewer sockets per user, 4 windows per shell (429); a ping every 30 s and a socket
  that sent neither a pong nor a message for a whole interval is terminated. Regression test:
  `apps/api/tests/ws-guard.test.ts` (units, plus 429 / 1009 / 1008 against a real hub).
- Residual (low, open): behind a reverse proxy the per-address cap counts the proxy's address
  (raw upgrades do not go through Express's `trust proxy`); it only holds while a credential is
  checked and agents reconnect with jittered backoff. Agent and instance-peer sockets are
  authenticated and keep only the size limit. Counts are per API instance.

### EXT-5 (medium, confirmed): MFA recovery codes

- Where: `apps/api/src/modules/auth/mfa.ts` `generateRecoveryCodes` (8 characters of a 32-letter
  alphabet = 40 bits), stored as plain `sha256(code)`; `POST /auth/login/mfa` read the code with a
  SELECT and marked it used afterwards with an unconditional UPDATE (the sign-in token and TOTP
  step the same way).
- Attack: with a copy of the database (a backup, a leaked dump) every 40-bit code falls to an
  offline SHA-256 search in minutes, giving the second factor for every account whose password is
  also known; one precomputed table covered all users. Online, two sign-ins sent at the same moment
  with one recovery code (or one TOTP code) could both get a session. Hashed at rest and rate
  limited online, hence medium.
- Fix: codes are 16 characters (80 bits, `XXXX-XXXX-XXXX-XXXX`), stored as SHA-256 over a version
  label, the user id and the code; the sign-in token, the TOTP step (`mfa_last_step < step`) and
  the recovery code are each consumed by a conditional UPDATE inside the sign-in transaction, and a
  lost race is refused (401) with nothing kept. Codes issued before this change (8 characters,
  plain hash) still work once, so nobody is locked out; regenerating (Settings > Account security)
  replaces them. Regression test: `apps/api/tests/account-security.test.ts` "issues 80-bit recovery
  codes ...".
- Residual (low, open): the old 8-character codes stay weak until used or regenerated; the UI does
  not yet ask the person to regenerate them.

### EXT-8 (medium, confirmed): file manager check-then-open race

- Where: `agents/endpoint-agent/internal/filemgr/filemgr.go`: `ValidateAndCleanPath` resolves links
  and checks the allowed roots and protected locations, then `downloadChunk`, `hashFile`,
  `uploadChunk`, `touch` and `copyRecursive` opened the file again by its name (an overwrite with
  `O_TRUNC`, before anything else).
- Attack: a local, unprivileged user on a managed computer owns a folder inside the allowed root
  (their profile). When a technician downloads, uploads or copies a file there, they replace the
  folder with a junction or symlink to a protected place between the check and the open. The agent
  runs as LocalSystem / root, so the operator's download returns `SAM`, a DPAPI blob or another
  user's file, and an upload overwrites or plants a file in a protected location. Needs local
  access and precise timing, hence medium.
- Fix: `openChecked` opens the file and checks where the handle really is
  (`GetFinalPathNameByHandleW` on Windows, `/proc/self/fd` on Linux, re-resolve plus same-inode
  check elsewhere) against the same roots and protected locations; reads, hashes and copies go
  through that handle; uploads open read-write without `O_TRUNC` and truncate, write and checksum
  through the checked handle; a file created outside is removed again. Regression test:
  `internal/filemgr/toctou_test.go` (swaps the folder for a junction at the exact moment through a
  test hook; download, hash, overwrite, new upload, touch and copy are refused and nothing outside
  is read, changed or left).
- Residual (low, open): `rename`, `move`, `mkdir` and `delete` act by path (`os.Rename`,
  `os.MkdirAll`, `os.RemoveAll`) after the check, so the same race can still rename or delete
  through a swapped folder. Closing it needs handle-relative operations (`openat`/`unlinkat`
  with `O_NOFOLLOW` on Unix, `NtCreateFile` with a root handle and `FILE_FLAG_OPEN_REPARSE_POINT`
  plus `SetFileInformationByHandle` on Windows), a larger change.
